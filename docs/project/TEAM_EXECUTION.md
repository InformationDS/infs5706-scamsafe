# 六人分工与执行规则

版本：v1 草案。日期：2026-10-15（Australia/Sydney）。适用范围：原型开发、测试、运行交付；不包含 PPT、讲稿、最终演示视频或答辩材料。

A 指项目发起人（你）；B–F 是其他五位成员的岗位代号，不代表已经指定真实成员或 GitHub 负责人。团队填入姓名、用户名、可投入时间及审核人后使用。当前应用、模型接入和测试数据尚未实现，本文不是完成情况报告。

需求以 [PRD](../product/PRD.md) 为准，字段以 [字段字典](../product/FIELD_DICTIONARY.md) 为准，接口要求见 [CONTRACTS](../architecture/CONTRACTS.md)。本文分配工作，不新增产品功能。

## 2. 目录与共享文件归属

下列模块路径是拟定归属，不表示目录或代码已经存在；技术栈确定后可调整实际路径，但需保持职责边界。

| 负责人 | 主要写入范围 | 与他人的明确边界 |
|---|---|---|
| A | `data/schemas/`、`docs/architecture/`、根依赖／锁文件／运行配置、未来 `app/state/` 与服务编排 | 定义共享状态和审核有效性，B 绑定界面、E 保存／渲染快照，均不另造一套规则 |
| B | 未来 `app/workspace/`、`app/chat/`、`app/forms/` 等界面模块 | 为 E 的历史／导出组件提供接入位置，不重写其存储和文件生成逻辑 |
| C | 未来 `server/model/`、`server/intake/`、`server/classification/`、`server/follow-up/` | 提供共用模型适配器；D 通过接口使用，不另建独立凭证或客户端 |
| D | `data/roles/`、`data/guidelines/`、未来 `server/guidance/`、`server/recommendations/`、`server/handover/` | 负责草稿内容及事实／指引引用；E 负责把同一内容呈现和导出，不再次调用模型重写 |
| E | 未来 `app/history/`、`app/storage/`、`app/export/` 等模块 | 持久化 A 定义的结构；只能消费有效审核快照，不能自行绕过或重定义审核 |
| F | `data/evaluation/`、`tests/`、`evidence/test-results/`，后续 CI 配置 | 可提出修复 PR，跨模块修改须先与负责人协调；不修改预期结果来掩盖实现失败 |

根依赖文件和共享 schema 由 A 统筹；其他成员提出所需依赖及理由，避免六个 AI 同时改锁文件。自己的任务交接文件由本人维护；汇总 STATUS.md 由 A 在集成时更新。

## 3. 每人具体工作包与完成条件

工作包编号用于拆分 GitHub Issue，和现有 TASK 编号的对应关系见第 9 节。当前全部为待实施计划。

### A：基础架构、契约与集成

| 工作包 | 具体工作 | 可验证交付 |
|---|---|---|
| A-01 | 组织确定技术栈、运行方式、配置示例，建立前后端脚手架及统一启动说明 | 第二台成员电脑可按说明启动基础界面和服务；配置不含真实凭证 |
| A-02 | 将字段语义整理为机器可读结构，确定枚举、ID、错误、版本和请求／响应样例 | 同一共享样例通过结构校验，B–F 明确自己输入和输出；117 个定义不变成 117 个强制输入框 |
| A-03 | 实现案件状态、版本、两次审核、失效规则与处理编排 | 更正事实、切换角色后相关输出需重审；旧请求结果不覆盖新版本；补问计数不被重置 |
| A-04 | 合并模块、解决接口集成问题、提供完整运行交付 | 一条真实模型流程跑通；执行文档完整；集成问题有归属和跟踪记录 |

A 不负责代写所有提示、指引、页面或 PDF 模板。遇到集成错误先确定接口方和修复负责人，再协调解决。

### B：信息／工作流区与聊天区

| 工作包 | 具体工作 | 可验证交付 |
|---|---|---|
| B-01 | 搭建双栏、阶段与状态展示，设计清楚的加载／失败提示 | 模拟数据下可查看当前角色、版本、阶段和轮次 |
| B-02 | 角色选项、自由描述、分组事实表单、原文依据、更正与首次审核 | 输入后字段可核对；未知和冲突可辨认；普通聊天回复不等于审核通过 |
| B-03 | 展示每轮最多 3 问、自由回答、未知／无法回答、提前结束 | 回答多个问题可以一次提交；问题与回答状态正确；错误不丢已有输入 |
| B-04 | 展示多机构建议、两次审核状态、统一摘要与接收方草稿，接入 E 组件 | 工作区与聊天共用案件状态，操作无须来回跳页，旧版本不冒充最新结果 |

B 可先使用契约一致且标记清楚的 mock，但必须在集成阶段接通真实服务。界面美化不替代完整流程。

### C：模型、提取、分类与补问

| 工作包 | 具体工作 | 可验证交付 |
|---|---|---|
| C-01 | 建立一个模型适配入口，统一结构化输出、错误分类及调用配置 | 可完成一次真实调用；凭证留在服务端配置；D 能复用相同入口 |
| C-02 | 从中英文自由描述提取多条事实，识别五类及多标签／其他／待确认 | 保留来源、未知和冲突，不凭空补齐；分类有对应事实依据 |
| C-03 | 生成并更新按需补问，结合 A 的计数与状态规则 | 0–3 问／轮、最多 3 轮／9 问；未知不重复问；回答或更正后重新分析 |
| C-04 | 处理超时、无效结构、引用错误和重试 | 错误可观察；重试不重复计数、不自动通过审核；同案新旧请求版本明确 |

提示与模型配置需要版本化；模拟调用和真实调用结果分开记录。C 不为缺少指引的事项编造机构规则。

### D：权限、指引、建议与交接内容

| 工作包 | 具体工作 | 可验证交付 |
|---|---|---|
| D-01 | 编写六类成员机构的合成岗位／权限配置和有限合成指引，组织团队审核 | 编号、版本、适用条件、职责、升级条件与审核状态可校验 |
| D-02 | 匹配案件事实、角色和指引，处理无匹配／失效／冲突 | 每条具体建议可追到有效指引和案件事实；不足时保留限制并提示人工核实 |
| D-03 | 生成相关机构路径，区分本岗位与其他机构，明确优先级和依赖 | 角色变化会改变可做事项；只列相关机构，允许并行事项 |
| D-04 | 生成统一摘要与各接收方交接内容 | 多份草稿事实一致，包含未核实项、交接理由、下一步和版本；不宣称已经发送 |

D 对合成规则和业务一致性负责；E 只负责确定内容的格式输出。D 与 F 核对案例参考结果，不能用系统生成答案反过来定义正确答案。

### E：案件历史、恢复与输出

| 工作包 | 具体工作 | 可验证交付 |
|---|---|---|
| E-01 | 本地保存与恢复、历史列表、案件切换、格式版本识别 | 刷新恢复角色、事实、轮次和审核版本；案件之间不混用信息 |
| E-02 | 接收 A 提供的有效审核快照，做选定草稿预览并和 B 集成 | 显示版本、接收方、未核实项和合成标记；失效快照不能当作最新审核记录 |
| E-03 | 从同一快照生成复制文本与 Markdown | 内容和预览一致，不重写事实；文件名包含案件、接收方、版本 |
| E-04 | 生成 PDF、处理失败和重试，检查中英文、表格、分页 | PDF 与 Markdown 正文对应；实际打开／渲染核对，无截断、漏页或乱码 |

测试用导出样本可作为必要证据保存；日常合成案件历史和临时导出留在本地，不混入共享评估集。

### F：评估、自动化验证与独立交付检查

| 工作包 | 具体工作 | 可验证交付 |
|---|---|---|
| F-01 | 编写 T01–T15 初始叙述、补问答案、岗位、预期结果和交互变体 | 五个完整、五个缺失／冲突、三个混合／其他／不足、两个权限／指引边界案例均可追溯并经交叉核对 |
| F-02 | 建评估工具与关键规则测试，组织执行方式 | 输出实际通过／失败、配置和原因；能定位字段、接口或行为错误，而非只对比一段措辞 |
| F-03 | 持续联调验收，记录缺陷、跟踪对应修复并复测 | 两次审核、版本、上限、指引、角色、导出等关键规则有证据；失败不被隐藏 |
| F-04 | 独立环境运行验证，协助建立真实可运行的 CI | 新克隆后按说明运行；自动检查实际执行，无空跑成功；模型凭证缺失时明确哪些检查未执行 |

测试从契约阶段开始，不等所有开发结束。各模块负责人先完成自己的验证，F 再进行独立检查。

## 4. 实施顺序与阶段门槛

未给出实际开发截止时间，因此采用可验证里程碑；团队安排日历后补充日期，不预设每天的投入或虚构工期。

| 阶段 | 主要执行 | 可并行工作 | 进入下一阶段的门槛 |
|---|---|---|---|
| M1 启动 | A-01、C-01 | B 界面草图；D 指引清单；E 保存／导出设计；F 案例草稿 | 基础程序可启动；真实模型连接有结果，或清楚标注模型阻塞及临时 mock |
| M2 契约 | A-02 | B–F 审阅自己接口，D／F 完善数据 | 共享结构与样例可校验，角色／状态／版本／错误含义一致 |
| M3 模拟流程 | B-01／02、A-03 | C-02、D-01、E-01、F-01／02 | 同一案件样例能走过界面与审核，mock 有标记 |
| M4 真实分析 | C-02 + B 接入 | D-02、E-02、F 验证提取／分类 | 自由输入能得到带来源的真实结构化分析 |
| M5 补问 | C-03、B-03、A-03 | D-03／04、E-03／04、F 验证状态 | 审核后补问可跑，未知／停止／上限／版本更新正确 |
| M6 建议与交接 | D-02／03／04、B-04 | E 格式输出、F 路径测试 | 一个案例有有效指引、相关机构建议和一致的多份草稿 |
| M7 第一条全流程 | A 集成、E-01 至 04、B 接入、F 验证 | C／D 迭代其他类型 | 真实模型下：输入→审核→补问→建议／交接→审核→复制／双格式导出；刷新可恢复 |
| M8 全量验收 | F-03、模块负责人修复 | A 协调整合 | 15 个案例及交互变体执行，关键规则通过，非关键局限明确记录 |
| M9 运行交付 | A-04、F-04，全员核对 | 各成员完善模块说明与交接 | 独立克隆可按说明运行，配置和已知局限齐全 |

M3 可以在模型暂不可用时推进；M7 和最终功能完成不能用 mock 代替真实模型。先用一个合成案例验证整条流程，不等五类全部调优才首次联调；共享分类结构从 M2 就包含五类与多标签。

## 5. 共同遵守的数据与接口规则

1. A 维护共享结构和版本；B–F 按契约消费，不在自己模块随意另造字段。字段定义变化先提交契约变更。
2. 每条事实保留来源、提取／核对状态；未知、否定、不适用、冲突分别记录，多笔交易和多次接触有独立 ID。
3. C 输出理解结果，D 输出建议内容，A 管理状态／版本，E 从审核快照输出文件。B 负责呈现，不在组件里再实现一份不同的业务决策。
4. 新请求和结果携带所用案件／配置版本；A 的编排拒绝过期结果覆盖新状态，C／D 提供足够的版本与引用信息。
5. 每轮和全案计数由确定的状态规则维护，不只依赖模型遵守文字提示。刷新、重试或角色切换不重置同案上限。
6. 审核有效性由代码校验；聊天中的“好”“继续”不自动通过审核。修改关键内容使相关审核失效。
7. 指引引用、岗位权限来自配置；导出不改变内容、不另调模型补写事实；生成草稿不等于实际完成转介。
8. 共享模型配置由 A／C 统筹，避免六人使用不同默认参数却声称结果一致。记录调用版本、运行方式与指引版本；凭证不进入前端、日志或仓库。

## 6. GitHub 执行流程

### 6.1 任务状态与责任

有对应 Issue 后，以 Issue 的负责人和状态为准；TASKS.md 仅维护索引、工作包与依赖。尚未建 Issue 的工作包保持“待创建”，不能编造 Issue 编号或把 A–F 代号当成真实 GitHub 账号。

建议状态：待开始 → 进行中 → 待审核 → 已合并待集成 → 已验收。阻塞时注明原因、需要谁提供什么、已经排查什么。仅生成代码、推送分支或发出 PR 不等于功能已验收。

一个工作包一位主负责人，可有协助人；每位成员同一时间优先完成一个主工作包，减少并行改动和集成积压。

### 6.2 开始与提交

1. 先看远端进展、当前分支和未提交改动，确认任务归属与依赖；不要清理或覆盖他人未提交工作。
2. 从最新 main 创建任务分支，例如 `feat/c02-case-analysis`、`feat/e04-pdf-export`、`test/f02-evaluation`。每人用独立克隆或独立工作区。
3. 在小范围内开发、执行验证，及时提交。不同模块的大规模重构不塞进同一个功能 PR。
4. 依赖缺失时可使用共享契约一致的 mock，但 PR、界面或测试报告明确标注；补上真实接入才算完成相应集成门槛。
5. PR 使用仓库模板，关联工作包／Issue、需求 FR 编号，说明改变的行为、接口、实际验证、剩余问题和影响消费者。
6. 小而完整的改动先审核合并，避免六人都拖到最后推送一大批代码。

### 6.3 审核与合并

- 至少一名非作者成员审核；按 A↔F、B↔E、C↔D 配对，涉及契约或跨模块时增加相关消费者。
- 审核检查逻辑、数据一致性、可复现验证、版本与来源、错误路径及是否覆盖约定范围，不只看页面截图或 AI 的总结。
- A 协调集成与合并顺序；合并前处理评审意见、必要检查和冲突。保护规则尚未配置时同样遵守此流程。
- 依赖 PR 先合并或明确基线，不用他人的未公开本地状态作为隐含依赖。
- 合并遇到冲突，相关文件负责人共同核对；不使用“全部采用本地／远端”来跳过语义判断，不擅自强推共享分支。

### 6.4 共享文件变更

PRD、字段字典、schema、根依赖、运行配置、模型适配器和状态定义属于共享文件。提出变更时写清原因、前后结构、消费者、兼容性、迁移与测试影响。A 统筹落地，相关成员审核；必要时先合并契约 PR，再分别更新消费者。

技术栈和依赖选定后，每个人沿用同一套配置和锁文件。成员需要新依赖时说明用途及替代方案，不让 AI 私自更换全项目框架。

## 7. 验证与完成标准

每个工作包完成至少包含：实现或配置、对应需求、可复现检查、必要文档、交接记录与已知局限。模块负责人执行自己的检查，F 进行独立验证。

| 负责人 | 示例验收情境（给定／当／则） |
|---|---|
| A | 给定一份已审核草稿；当修改关联关键事实；则旧审核不再允许作为新版本的导出依据 |
| B | 给定有缺失和冲突的分析结果；当员工查看表单；则能区分字段状态并找到原文依据 |
| C | 给定信息不全的案例；当生成一轮补问；则只出现最多 3 个有字段和原因依据的问题 |
| D | 给定没有适用有效指引的事实；当生成处理建议；则不会出现虚构指引引用或无依据的确定处理动作 |
| E | 给定同一有效审核快照；当下载 PDF；则其事实、接收方和未核实事项与对应 Markdown 一致 |
| F | 给定固定案例与预期结果；当运行评估；则输出实际结果和可定位的失败证据，标明 mock 或真实模型 |

关键规则检查包括：不编造事实／引用；未知不当作否／0；多记录不丢失；补问上限；岗位权限；两次审核与修改后失效；多份交接一致；保存恢复；同快照输出。PDF 实际打开或渲染核对，不能仅用生成成功代替。

F 维护 15 个固定案例，D 协助核对业务预期；不能以当前系统输出直接充当标准答案。改变案例或预期时说明参考错误或需求变化，并记录版本，不用降低标准掩盖失败。

验证报告写明环境、代码提交、模型／mock、指引版本、案例、预期／实际和通过／失败。凭证不可用时标注未执行的真实模型检查，不伪造通过结果。

应用尚未建立，因此不能提前提供虚假的 build/test 命令或 CI 成功状态。现有资料检查命令为 `python scripts/maintenance/check_repository.py`，它只验证仓库资料。

## 8. 每位成员使用 AI 的工作流程

### 开工前

让 AI 阅读 AGENTS.md → AI_START_HERE.md → STATUS.md → TASKS.md → 本文对应角色 → 任务相关 PRD／字段／契约。只在需要时读原始参考内容，不默认扫描所有页图。

先让 AI 说明：当前分支和项目状态、自己的工作包、输入输出和依赖、计划修改的文件、验证方式；再进入实现。需要修改共享结构时先显式提出影响，避免跨成员接口漂移。

### 实施中

一次推进一个可验证的小步骤。读取现有接口和其他成员交接，不凭空假设已有功能。生成后由成员检查关键逻辑，至少运行对应样例与错误路径。发现接口不一致先记录和协调，不把其他模块整体重写。

### 完成后

让 AI 给出真实 diff 摘要、实际运行命令及结果、未完成项、接口影响和交接文件。成员能解释自己模块的主要逻辑、提示设计、失败情况和依赖后再提交审核。

可复制的任务启动提示：

```text
你正在协助 ScamSafe 小组项目。我是成员 [A/B/C/D/E/F]，本次只负责工作包 [编号]。
先按 AGENTS.md 和 AI_START_HERE.md 读取当前状态，再读 TEAM_EXECUTION.md 中我的职责、
相应 PRD、字段和接口约定。检查当前分支和已有改动。
请先说明输入、输出、依赖、拟修改文件及验收方法，再分小步骤实现。
保持共享契约一致，保留其他成员修改。实际运行相关检查；mock、未测试和阻塞要明确写出。
结束时更新本工作包交接记录，报告变更、验证结果和剩余问题。
```

## 10. 沟通、阻塞与变更

- 每个工作时段开始同步依赖和远端进展；结束前提供“完成、验证、阻塞、下一步”的短交接。
- 跨模块接口、根依赖、角色或指引版本变化，需在相关 Issue／PR 明确标注消费者，并向受影响成员交接。
- 阻塞时提交最小复现：输入、角色／版本、预期、实际错误、已尝试方法、需要谁提供什么。不要仅写“AI 跑不通”。
- 负责人按问题归属修复自己的模块；A 协调跨模块问题，F 复测。需求变化先记录决定和影响，再修改实现。
- 所有会影响结果的决定落到仓库或 Issue；聊天中的临时约定不能长期作为唯一接口说明。

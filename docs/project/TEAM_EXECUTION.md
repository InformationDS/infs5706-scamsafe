# 六人分工与执行规则

更新时间：2026-10-17（Australia/Sydney）。适用范围：原型开发、验证和运行交付。当前基础程序尚未实现；本文分配责任，不表示功能已经完成。

A 为项目发起人；B–F 是其余成员的岗位代号，真实成员尚待在 [TEAM](TEAM.md) 中登记。产品行为以 [PRD](../product/PRD.md) 为准；[完整案件样例](../product/examples/WORKED_CASE.md)用于理解和核对同一条流程。

## 1. 谁负责什么

A 准备基础版本、确定产品规则、建立可运行基础并填好任务卡；B–F 和其 agent 按指定步骤核对或作限定修改。任务不要求成员理解研发流程后自行设计。涉及代码时，A 先给出可运行入口、允许修改的文件和可观察的预期，成员再让 agent 执行。

| 角色 | 主要交付 | 开工前由 A 提供 | 本人检查的结果 |
|---|---|---|---|
| A（你） | 产品规则决定、起始版本、技术选型、运行骨架、共享结构、状态／审核、模型调用、保存恢复、导出基础、检查工具、技术审核和集成 | 为其他成员准备实际文件、固定输入、逐步操作和明确预期 | 公共规则正确，模块可以连接，真实验证与限制有记录 |
| B | 按现有操作稿核对入口、字段、提示，在指定页面或组件内作限定修改 | 已填操作稿；代码任务另需可启动页面、指定组件和固定状态 | 每步入口找得到、操作能完成、提示看得懂；记录与稿件的差异 |
| C | 在已有基础提示上每次调整一处，记录固定输入的前后结果 | 已填基础提示、固定输入与预期；运行任务另需模型入口和输出结构 | 对照同一输入记录漏项、无依据内容和补问差异；不自行改字段或分类规则 |
| D | 按已填样板整理合成岗位和指引，逐项核对条件、权限、事实和引用 | 已填条目、产品规则、固定案件及待核对清单 | 标出缺项和冲突；新业务规则交 A 决定，不自行批准预期 |
| E | 用固定正文调整排版；有导出基础后核对预览、复制和导出 | 固定正文、已填排版稿；代码任务另需有效快照、基础导出和指定模板 | 正文无增删、内容一致；PDF 可生成后逐页检查 |
| F | 按给定输入、步骤和预期执行检查，记录差异并按相同步骤复测 | 已填案例和预期、操作清单；运行任务另需已验证入口或命令 | 独立记录预期与实际；未明确的标准交 A 补齐，不从系统输出反推答案 |

共享结构、状态、审核有效性、模型适配器、保存恢复、运行配置、依赖和检查工具由 A 统筹。B–F 发现需要改动这些内容时，把输入、现象和所需帮助写入任务记录并交给 A；不要求成员自行设计替代方案。D 可以整理指引和权限内容，内容中的规则由 A 确认，执行规则的公共机制由 A 实现。

## 2. 三个实施阶段

| 阶段 | 工作重点 | 可以并行的内容 | 完成条件 |
|---|---|---|---|
| 准备共同基础 | A 先确定近期技术方案，再建立运行骨架、共享结构和一个案件的固定样例 | B–F 补充或核对已填起始稿；无需等待所有材料齐备 | A 实际验证启动和检查步骤；已满足条件的小任务可发布，缺失依赖的卡仍标为阻塞 |
| 跑通一个案件 | A 接通公共流程；B 展示、C 提示、D 内容、E 模板、F 操作验收 | 已满足各自开工条件的小任务 | 一个案件在真实模型下完成输入、审核、补问、建议、交接、再审核、输出和恢复；失败与未完成项明确记录 |
| 扩展与交付 | 按同一模板扩展 15 个案例，修复缺陷并复测 | 独立内容任务与已隔离的界面／模板调整 | 按 PRD 完成关键规则验收；F 在独立环境按说明运行；已知限制和真实结果可追溯 |

近期顺序是：A 确定技术与运行方案 → 建立骨架并接通一个固定案件 → 把已就绪入口拆成小代码任务交给成员 → 单例通过后逐步扩展到 15 例。不要求六份准备稿全部审核完才开始骨架；只等待本次实现实际需要的规则和输入。

模拟结果可以支持界面、排版和操作开发；任务卡必须说明模拟范围。真实模型不可用时，相应真实集成验收保持未完成。首批文稿任务以已填起始稿为输入，只补充或核对规定内容；稿件完成不表示代码任务已可开工。

## 3. 如何领取和完成一个任务

[任务索引](TASKS.md)是入口；具体卡放在 `docs/project/tasks/`，使用 [任务卡模板](tasks/TEMPLATE.md)。TASK-005 至 TASK-011 表示工作方向；具体执行使用其下的小卡编号，例如 [TASK-007-01](tasks/TASK-007-01.md)。

每张卡只交付一个能检查的结果，写清目标、实际读取与允许修改的文件、准备好的输入样例、顺序步骤、验证操作与预期、停止反馈条件和验收要求。程序任务必须列出已存在的入口和经过验证的命令。创建新文件时，应明确标为本任务产物。模板没有填完、负责人没有确认或开工条件没有满足，均不可领取；不让 agent 自行补出前置设计。

1. **开工：** A 确认负责人和开工条件；成员读取自己的任务卡、AGENTS 和卡片指定内容，按卡片顺序操作。每人先完成一个主任务。
2. **执行：** agent 只修改允许范围；成员亲自按步骤观察结果。看到错误、找不到指定文件、需要更改共享规则或实际结果与预期不符时，记录问题交给 A。
3. **提交检查：** 在唯一任务记录中填写实际结果和未完成项，附代码变更或 PR。只生成代码或 agent 声称通过，不能标为完成。
4. **验收：** 成员或 F 核对可观察结果；A 审核技术变更并集成。达到任务卡完成条件后，才标为已验收。

### 任务说明与执行记录

- **任务卡始终维护执行说明：** 目标、范围、输入、步骤和验收条件都保留在本地任务卡；需要调整时由 A 确认后更新卡片。Issue 链接任务卡，不复制这些说明。
- **已有对应 Issue：** Issue 是该任务的唯一负责人、状态和实际执行结果来源；本地卡移除这些动态记录，改为链接 Issue。
- **尚无对应 Issue：** 对应本地任务卡记录负责人、状态和结果。A 协调分配，避免不同电脑上的成员重复领取。
- TASKS 仅索引任务和依赖；STATUS 由 A 汇总实际集成情况。是否已建立 GitHub 仓库不改变上述判断。
- 建立 Issue 时，将本地卡当时的负责人、状态和实际执行结果转入 Issue，并将卡内这些动态部分替换为 Issue 链接。任务范围、步骤和验收条件继续在卡内维护；Issue 中记录相关说明变更及链接，避免重复抄写。
- 仅在跨任务接手需要单独说明时使用 [handoffs](handoffs/README.md)，日常结果直接写在 Issue 或本地任务卡中。

状态使用：`待指派` → `进行中` → `待审核` → `已验收`。阻塞单独注明原因和“需要谁提供什么”，解除后重新检查开工条件。待指派不代表开工条件已满足；代码已合并但尚未验证的任务仍为待审核。

## 4. 审核和 Git 协作

成员互审只检查能观察的行为：按照步骤是否能运行、输入输出是否符合样例、操作提示是否清楚、内容是否遗漏。可由 B／E 互看界面和导出，C／D 核对分析依据，D／F 核对案例预期；这些检查不等于技术签核。

A 负责代码、接口、错误处理、状态和数据一致性的技术审核。A 自己的技术改动应附实际检查结果，由 F 独立执行操作清单并记录结果；记录中明确作者自检和 F 行为验收，不写成已有另一位成员完成技术审核。关键规则缺少证据时保持待审核。

A 分配前确认工作副本、允许文件、结果位置和交付方式；只有 Git PR 方式另需基线、任务分支及目标分支，文件交 A 不依赖这些 Git 信息。可照做的操作见 [CONTRIBUTING](../../CONTRIBUTING.md)。成员保留他人改动，不直接推送默认分支，不自行解决冲突或强制覆盖文件；遇到冲突记录现状交给 A。每次 PR 只对应一个任务卡的交付，使用[仓库 PR 模板](../../.github/pull_request_template.md)。A 按授权完成合并和集成。

## 5. 验证与反馈

验证必须有输入、操作、预期和实际结果。标明模拟或真实模型；未执行就写未执行及原因。F 记录缺陷时附任务编号、复现步骤、预期、实际和截图／输出位置，修复后重复相同步骤。预期由 A 根据产品规则和已确认指引填写；D／F 核对预期与材料是否一致，发现标准缺失或矛盾时交 A 处理，不能自行改标准来让结果通过。

当前可运行的资料检查是 `python scripts/maintenance/check_repository.py`，从仓库根目录执行。它不证明应用功能通过。通用启动、应用测试和导出命令尚未建立，由 A 实现并验证后写入具体任务卡。

成员可复制以下提示，先填入一张已指派且满足开工条件的实际任务卡：

```text
请按 AGENTS.md 和任务卡 [实际路径] 完成本次任务；若有 Issue，请从卡内链接查看负责人和执行状态。
只读任务卡指定资料，只改允许范围，保留已有改动。
先核对开工条件和指定文件；缺少输入、命令或前置功能时记录阻塞，不自行补做架构。
按卡片步骤执行并报告每项检查的实际结果。模拟、真实模型和未执行项分别说明。
需要改变共享结构、运行配置、状态规则或任务目标时，说明问题交给 A。
完成后只更新该任务的唯一记录，并给出让成员亲自操作核对的步骤。
```

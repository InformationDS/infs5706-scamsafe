## 目标与开工条件

产出一份可供后续搭建使用的统一技术决定，不在本卡安装框架或编写应用。A 可以先整理方案；模型预算、运行环境或截止时间未知时将它们逐项列为待决定，不能假设已获得凭证或付费授权。

## 读取与修改范围

- 读取：[PRD](../../product/PRD.md)、[架构入口](../../architecture/README.md)、[接口要求](../../architecture/CONTRACTS.md)、[完整样例](../../product/examples/WORKED_CASE.md)。
- 本任务创建：`docs/architecture/IMPLEMENTATION.md`。只写本次技术决定；其文件名不是声称当前已存在。
- 更新本卡的 Issue 链接或执行结果；其余文件由后续任务处理。

## 输入与步骤

1. 用完整样例核对所需能力：英文界面／输出、中英文输入、两次审核、本地保存、双格式导出。
2. 向 A 本人确认开发电脑条件、是否需要线上运行、模型接入条件、预算限制和截止日期；未知项明确写未知。执行 agent 不代替 A 承诺这些条件。
3. 在新文件按以下固定栏目填写：已确认运行条件；选定技术及理由；模型／凭证配置方式；本地保存和 PDF 方案；准备建立的运行与检查入口；未决项及影响。
4. 每个技术方向给出一套拟采用方案，明确哪些已决定、哪些因条件缺失未定。只记录可核实的事实，不写未执行的安装命令为“可用”。
5. A 确定方案后，另开“建立运行骨架”任务：该任务完成时才发布实际启动命令和成员代码入口。

## 人工检查与完成条件

打开新文件逐项检查：每项首版能力有对应实现责任；只有一套已确定方案；凭证用占位；外部条件有证据或明确未知。A 明确确认后可验收本方案任务。仍影响选型的关键条件未知时保持阻塞，允许提交方案草稿，不能标为已验收。

## 停止与反馈条件

需要付费、真实凭证、改变首版范围或尚未确定的部署承诺时，将具体所需条件交 A。不要为了完成方案而声称应用已能运行。

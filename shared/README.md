# Shared foundation contract

Import schemas, types, fixture constructors and pure operations from `shared/index.ts`. Case state is synthetic and `mode:mock`; role and guideline schemas deliberately require disabled/pending content. This foundation cannot activate business configuration. Model analysis provenance can be `source:model` while the surrounding training case and outputs remain unapproved; a real network response does not approve content.

`FactRecord` uses flattened `fieldId` and optional `recordId`, typed `value`, independent `version`, extraction/review status, `sourceIds`, conflict candidates and employee history. Repeated records share field IDs and differ by record ID. `AnalysisResult` carries types, reasons, alternatives, gaps and fact proposals, never employee permissions or valid guidance. `AnalysisEnvelopeSchema` fixes `{facts, analysis, questions}` for content experiments. The current HTTP adapter returns analysis and metadata; it does not create question rounds. Case state owns question counters, role selection and reviews. Model proposals cannot mutate those structures.

The runtime fact validator covers the necessary single-case semantics: E04 is a finite number or null; C08/F01/G01/G05/H08 are boolean or null; E05 is a string or null without an invented currency whitelist. The same restrictions cover current values, conflict candidates and history. C/D/I/J facts and E02–E09 require record IDs; `case.facts` contains A–J only. A literal false differs from unknown null. This is not a complete implementation of all 117 field meanings. These field-dependent refinements are runtime checks and are not fully represented by the generated JSON Schema value union.

`RecommendationSchema` separately defines the future recommendation boundary: ID/version, responsible role, step, priority/reason, dependencies, exact fact targets, guideline IDs/versions, limits and a simulated employee decision. Decisions are pending/accepted/modified/rejected; modification and rejection need a reason. Every instance remains `simulated:true` and content approval pending. This schema creates no recommendations and enables no guidance. `CaseRecord.recommendations` is optional; output references must resolve to those records, and each recommendation fact target must exist in the case. Guideline references still require separate future configuration validity/permission checks before any business use.

`SummarySchema` identifies an independent summary. `HandoverDraftSchema` additionally requires a recipient ID/title and recommendation IDs. Base `OutputRecord` retains these as optional for the existing consumer interface. The teaching handover fixture supplies concrete synthetic recipients with an empty recommendation-reference array: its copied target prose illustrates unapproved content, not generated effective recommendations. A summary cannot have a recipient. These structures distinguish draft content, recommendation decisions and employee review records rather than treating them as one object.

`mergeAnalysis(record,incoming,requestCaseVersion)` preserves employee corrections and history, rejects unknown source references and context/derived/review targets, and does not invalidate unchanged analysis merely because transport provenance changes. `applyAnalysisResult(record,incoming,{caseVersion,requestId},currentRequestId)` additionally ignores superseded requests for the same version. HTTP callers must use both the current request ID and the case version, not only response order. The low-level merge function alone does not establish which request is newest.

`correctFact`, `confirmFacts`, `answerQuestion`, `stopFollowUp`, `replaceOutput` and `reviewOutput` preserve history and return changed state. A mutation is unsaved until the actual transaction succeeds and the caller uses `markSaved`. `answerQuestion` accepts optional `{target,value}` proposals only for its own target; unknown answers cannot create facts. `addQuestionRound` only records rounds after its caller supplies successful display-and-save confirmation; the browser still owns the real transaction. Later answers update the original question without changing counts or reopening stopped questioning.

Output dependencies use keys `fact:<fieldId>:<recordId-or-empty>`, `analysis`, `role` and optionally `output:<id>` or `case`. Dependencies should include only actual content inputs. `isReviewValid` checks output version and current dependencies. Employee-facing export must use `buildSnapshot`, which also blocks unsaved states and unconfirmed fact changes. `ExportSnapshot` holds one object, one body, identity/version metadata and explicit simulated-review/pending-approval markers. Markdown and PDF render the same snapshot body; layout code does not decide review validity.

`npm run schemas` generates JSON Schema from Zod. JSON Schema describes shape; cross-record references, counts, conflict protection, dependency invalidation and latest-request guards require the runtime schemas and core functions as well. `npm run fixtures` regenerates fixed JSON states. Never edit generated fixture state to invent content approval. Approved content is registered separately in `data/business/`; legacy fixtures remain pending simulations. New runtime ports are an A01 deliverable, not currently implemented; B/C/D/E build their domain modules against those ports, and A02 integrates them.

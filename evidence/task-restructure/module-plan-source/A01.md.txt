# A01：接入获批业务配置与运行数据结构

## 目标与责任

目标：接入获批业务配置与运行数据结构，只完成本卡范围。建议角色：A；实际成员由 A 人工指派。产品规则：FR-01, FR-02, FR-09，以卡内指定PRD条款为准。

## 开工条件

依赖：无开发任务依赖；使用当前已验证公共基座。

技术输入已具备；A 指派实际成员并提供完整工作副本后可开工。

A 指派时在下方唯一执行记录确认工作副本实际绝对路径；Windows 可使用当前项目目录，macOS 使用成员自己的项目根目录。没有完整文件、存在未交接改动或检查失败时保留现场，交 A 判断。不得按远端文件存在推定本地新增文件已发布。

## 顺序步骤

1. 先运行 npm run check 和 npm run check:business，核实当前 pending 模拟状态与独立 approved 业务包，不能只删除 schema 的字面量约束冒充接入。
2. 在 shared/schema.ts 建立运行案件、配置批准、员工实际审核的独立身份与来源边界；保留可明确识别的模拟检查输入。运行案件支持动态案件号、重复记录、来源、版本和两个审核阶段。
3. 在 shared/workflow.ts 建立运行流程公共入口；从 loadBusinessBaseline 读取当前获批岗位、接收方和指引，用于创建未审核案件。配置批准不可自动产生首次或最终员工审核。
4. 确认模型提议、员工更正、建议选择及内容版本分别持久化；旧模拟快照不能被解析为正式审核。扩展已有 schema 生成器，生成受影响 schema 并更新契约。
5. 增加结构与批准身份负向检查，运行 npm run schemas、npm run check、npm run check:business 和 npm run build；记录新公共函数签名及运行案件固定构造输入。

## 固定检查与预期

| 输入／操作 | 应观察到的结果 |
|---|---|
| 当前业务包创建新案件 | 岗位可用、事实未审核、无员工最终审核；内容批准只来自包登记 |
| 把 simulated review 填入运行案件 | 不得变为真实员工审核；无有效审核不能生成正式快照 |
| TX-01 与 TX-02 同字段 | 各自有稳定编号和来源，未知、否定、不适用、冲突不合并 |

命令从本副本项目根目录执行；Windows使用npm.cmd，macOS使用npm。只执行本卡步骤要求的检查；需要浏览器时先构建并安装Chromium。前置新建命令由A实际验证后填工作包，成员不猜命令。

## 停止、审核与完成条件

缺输入、接口冲突或需要范围外修改时，保留现场并停止受影响步骤，按[AGENTS](../../../AGENTS.md)报告具体缺项；不自行补架构、改业务规则或标准答案。

成员填写实际观察，A审核技术与集成。本卡要求的交付与检查有证据、相关问题解决且A确认后才标已验收；不继承基座通过结论。

证据写evidence/task-results/A01/run-01/；复测使用run-02等新批次，保留首次失败。
